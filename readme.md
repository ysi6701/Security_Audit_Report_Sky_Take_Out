## 2. 项目简介（Project Introduction）

Sky Take Out（苍穹外卖）是一个基于 Spring Boot 的在线外卖订购系统开源实现，代码仓库公开发布于 GitHub。
根据仓库 README，该项目面向典型餐饮外卖业务场景，覆盖商家后台管理与用户下单两类核心业务流程，属于较为完整的前后端分离式业务系统示例。
仓库首页显示该项目采用多模块 Maven 结构组织，主要包含`sky-common`、`sky-pojo`与`sky-server`等后端模块。

从业务属性来看，该项目涉及账户认证、菜品与套餐管理、订单处理、地址簿、购物车、支付相关配置以及 Redis/MySQL 等基础设施接入，因此天然具有较高的安全敏感性。
一旦在认证授权、接口访问控制、敏感配置管理、支付参数保护、文件访问、日志输出或数据存储等方面存在缺陷，可能进一步影响用户隐私、订单数据、商户运营数据乃至服务可用性。

结合本次审计实际情况，审计工作主要围绕后端服务与客户端交互接口展开；前端页面与交互逻辑未作为本轮重点审计对象，因此本报告结论更侧重于服务端实现安全性、接口暴露风险以及运行配置层面的安全问题，不对前端渲染层的安全性作完整覆盖性评价。

## 3. 技术栈与架构特征（Technical Architecture）

### 3.1 后端技术栈
- Java 17
- Spring Boot 3.1.2
- MyBatis
- Maven 多模块工程

### 3.2 数据存储与中间件
- MySQL（业务数据持久化）
- Redis（缓存、验证码/会话辅助、业务状态存储）

### 3.3 前端技术栈
- Vue
- Uniapp
- ElementUI

>注：本次审计重点放在后端及客户端对应的服务端接口实现，前端代码未作为本轮完整审计重点对象。

### 3.4 系统架构特征

- 典型前后端分离架构
- 后端以 RESTful API 形式对管理端与客户端提供服务
- 使用 Maven 进行多模块拆分，主要包括：
  - `sky-common`：公共工具类、通用配置与基础能力 
  - `sky-pojo`：实体类、DTO、VO 等数据模型 
  - `sky-server`：核心业务逻辑、控制器、鉴权及接口实现
- 部署层通过 Nginx 进行反向代理与静态资源转发：
  - `/api/`代理至后台管理端接口 
  - `/user/`代理至客户端接口 
  - `/ws/`提供 WebSocket 通信能力

### 3.5 安全架构特征
经审计，系统当前安全架构主要呈现如下特征：
- 系统采用前后端分离与统一 API 暴露模式，接口边界较清晰，但一旦认证鉴权链路存在缺陷，风险影响范围将覆盖后台与客户端多个业务接口；
- 项目同时包含后台管理端与普通用户端两类访问入口，天然存在角色边界与权限隔离需求，需重点关注横向越权、未授权访问及接口访问控制粒度不足等问题；
- Redis、对象存储/文件上传、WebSocket、支付相关配置等外部依赖均可能成为攻击面，安全风险不仅来源于业务代码，也可能来源于默认配置、敏感参数管理及依赖组件使用方式；
- 项目公开文档中体现出较多运行配置与部署细节，说明系统具备较强的可复现性，但同时也意味着若默认配置、安全基线或密钥管理不严，真实部署环境中较易出现敏感信息暴露、弱口令复用、调试接口外露等问题；

从本轮审计重点来看，后端与客户端服务端接口是主要风险承载面，而前端层面的 DOM 型问题、前端依赖供应链问题及浏览器侧安全策略问题，尚未在本轮审计中完成系统性覆盖。

## 4. 审计目标与范围（Audit Scope）

本次审计的核心目标是识别 Sky Take Out 开源版本在服务端实现及客户端相关接口中的安全风险，评估其在身份认证、权限控制、敏感信息保护、输入处理、文件与对象访问、配置安全、依赖组件安全以及接口暴露面等方面的防护成熟度，并据此给出风险评级与修复建议。
审计关注点不仅包括可直接导致未授权访问、数据泄露或业务绕过的高危问题，也包括会在实际部署中放大攻击面的配置类与基线类缺陷。

结合实际审计情况，本轮审计范围主要包括：
- 后台服务端（Admin/Server Side）：重点关注后台管理接口、认证鉴权逻辑、业务接口访问控制、数据操作边界、异常与日志处理、配置文件以及第三方依赖使用情况；
- 客户端相关后端接口（User/Client APIs）：重点关注面向普通用户/小程序客户端暴露的接口安全，包括令牌校验、越权访问、参数校验、业务对象引用安全及潜在数据泄露问题；
- 运行与配置层面：重点审视公开仓库中体现出的数据库、Redis、JWT、Swagger/Knife4j、Nginx 代理及外部服务接入配置的安全性。

本轮未完整纳入审计范围的部分主要为前端实现，包括管理端页面、Web 前端脚本、客户端前端页面逻辑、DOM 注入类问题、前端依赖供应链问题以及浏览器侧安全策略（如 CSP、前端鉴权展示逻辑等）。
因此，报告中若涉及前端风险，多为基于接口与架构暴露面作出的间接判断，不构成对前端安全性的全面审计结论。

为避免结论外延过大，本报告默认基于 GitHub 仓库公开代码、公开配置与可见项目说明进行分析，不覆盖生产环境部署差异、云上网络边界策略、真实支付网关配置、CI/CD 流水线、主机加固状态以及未公开私有组件。
如实际运行环境与开源仓库存在差异，则具体风险等级可能随部署方式、网络暴露面及密钥管理成熟度发生变化。

## 5. 核心审计发现（Key Audit Findings）
结合对 Sky Take Out 项目后台服务端及客户端相关后端接口的审计情况，系统当前存在的安全问题主要集中在访问控制、身份认证、核心业务逻辑、支付安全、组件使用、可用性防护、数据保护及输入校验等方面。
部分问题属于高危甚至致命级缺陷，一旦在真实生产环境中被利用，可能直接导致用户数据泄露、订单业务被篡改、支付流程被伪造、后台权限被滥用，甚至进一步影响服务器与内部业务网络安全。

本次审计发现可归纳为以下六个方面：

### 5.1 越权访问与身份认证漏洞(Broken Access Control & Authentication)

该类问题是本次审计中出现最为集中、影响范围最广的一类问题，直接关系到系统账户体系、业务数据边界以及后台管理能力的安全性。
系统在多个核心模块中普遍存在对象归属校验不足、角色隔离不严以及认证机制薄弱等问题。

#### 5.1.1 水平越权（IDOR）

系统在多个面向用户的数据对象操作中，未能严格校验资源是否归属于当前登录用户，存在典型的 Insecure Direct Object Reference（IDOR）问题。
攻击者可通过构造或遍历对象 ID，访问、修改或删除本不属于自身的数据。

具体表现包括：
- 订单模块：未严格校验订单归属关系，普通用户可对其他用户订单执行查询、取消、催单、再来一单等操作；
- 地址簿模块：未校验地址记录归属，用户可遍历、修改、删除他人地址信息，甚至覆盖他人收货数据；
- 员工管理模块：员工之间缺乏严格对象边界控制，存在任意禁用/启用其他员工账户、修改他人资料等风险。 

此类问题会直接导致用户隐私泄露、订单业务异常及后台账户体系被滥用，属于高危访问控制缺陷。

#### 5.1.2 垂直越权（Privilege Escalation）

系统后台权限模型设计较为粗放，普通员工与高权限管理角色之间缺乏有效隔离，导致低权限用户可执行本应仅限管理员或超级管理员的敏感操作。

具体包括：
- 角色边界缺失：后台普通员工可执行接近全局管理员级别的操作，缺乏“超级管理员”或高权限角色隔离；
- 经营数据暴露：普通员工可访问全局经营统计、营业数据等敏感信息；
- 高危后台操作未隔离：如店铺状态切换、分类新增/删除、重要业务配置修改等操作，未建立足够严格的权限边界；
- 套餐访问控制不足：客户端未严格校验套餐当前状态，用户仍可能访问已下架或不应展示的套餐资源。

该类问题将直接削弱后台管理安全边界，导致低权限账户在实际效果上等同于管理员账户。

#### 5.1.3 认证与会话管理缺陷

在认证与会话安全设计方面，系统存在多项基础性缺陷，攻击门槛较低，易被自动化攻击或凭证滥用所利用。

主要问题包括：
- 密码存储不安全：后台员工密码仅使用弱 MD5 进行存储，缺乏现代密码散列保护机制；
- 默认密码过弱：默认口令设置为 123456，且未强制用户首次登录后修改密码；
- 缺乏爆破防护：登录接口未设置验证码、失败次数限制、账户锁定、IP 限制等防暴力破解措施；
- 会话失效机制不完整：登出操作仅返回成功提示，JWT 并未在服务端失效，缺乏 Redis 黑名单、Token 版本控制或主动吊销机制。

上述问题叠加后，意味着攻击者可通过撞库、爆破、令牌复用等方式较低成本地接管后台或普通用户账户。

### 5.2 核心业务逻辑与支付漏洞 (Business Logic & Payment Flaws)

该类问题直接影响订单处理、支付状态与资金安全，是本次审计中风险等级最高的一组问题。
若被恶意利用，不仅会破坏业务流程完整性，还可能直接造成资产损失。

#### 5.2.1 支付回调安全校验缺失

支付回调处理逻辑缺乏关键安全校验，无法有效确认通知来源真实性与支付结果完整性。

具体表现为：
- 未校验支付签名：微信支付回调未严格校验签名、时间戳、随机串等关键字段，存在被伪造“支付成功”通知的风险；
- 未校验订单金额：回调处理中未将支付金额与订单实际应付金额进行一致性校验，可能导致低金额支付替代高金额订单；
- 业务信任前端价格：购物车或下单过程中对价格字段保护不足，存在前端参数可篡改空间，攻击者可通过修改价格参数影响最终订单金额。

上述问题属于典型的支付链路高危缺陷，严重情况下可造成“低价购买高价值商品”或直接伪造已支付订单。

#### 5.2.2 业务状态机与幂等性缺失

系统在订单处理等关键业务流程中，对并发竞争和重复请求缺乏充分防护，存在状态机紊乱与重复操作风险。

主要包括：

- 并发状态冲突：接单、拒单、取消订单等流程未充分处理并发场景，可能出现订单状态竞争、覆盖或错乱；
- 接口缺乏幂等控制：关键操作未建立请求去重或幂等校验机制，存在重复派单、重复执行状态变更、重复扣款等潜在风险。
- 这类问题虽然不一定由单一漏洞直接触发，但在高并发或恶意重放请求条件下，极易演化为严重业务事故。

#### 5.2.3 业务完整性与合规性校验不足

系统在多个业务提交环节缺乏必要的关联性校验与返回值校验，导致业务逻辑可被绕过或被错误执行。

例如：
- 下单时未充分校验提交的地址 ID 是否真实归属于当前用户；
- 未对外部接口返回结果中的关键状态字段（如 errcode）进行严格判断，可能引发业务误判或异常流程继续执行。

该类问题会导致业务完整性下降，在支付、下单、配送等关键链路中形成隐蔽风险。

### 5.3 高危技术栈与架构漏洞 (Critical Technical & Component Vulnerabilities)

除业务逻辑问题外，系统在文件处理、外部资源访问及组件使用方式上也暴露出若干高危风险。
这些问题一旦与鉴权缺陷、令牌泄露或部署失误叠加，可能被进一步利用为服务器级入侵入口。

#### 5.3.1 任意文件上传风险

系统上传接口对上传内容的约束不足，存在较高的危险文件落地风险。

主要问题包括：
- 上传接口仅依赖文件后缀名进行类型判断；
- 未严格校验 MIME 类型、文件头特征及内容合法性；
- 未限制文件大小与上传类型范围；
- 上传文件可直接落地于可访问目录，结合认证绕过或令牌泄露后，存在进一步被利用进行恶意文件投递甚至 GetShell 的现实风险。

该问题属于高危文件处理缺陷，在生产环境中应优先修复。

#### 5.3.2 SSRF 与反序列化潜在风险

系统对外部 URL 访问边界控制不足，且 Redis 等组件使用方式缺乏足够安全限制，存在进一步演化为服务端请求伪造或反序列化利用的空间。

具体表现为：

- 外部 URL 访问缺乏协议、目标地址、内网网段等限制，存在 SSRF 潜在利用面；
- Redis 若缺乏序列化安全约束、访问边界控制及输入限制，可能形成反序列化或缓存投毒风险。

尽管此类问题在开源代码中未必都形成直接可利用链，但从架构与组件使用方式来看，具备较明显的安全隐患。

#### 5.3.3 通信安全与中间人攻击风险

系统在外部通信过程中缺乏充分的证书校验与安全传输约束，可能导致通信内容在传输链路中被窃听或篡改。

若系统对 HTTPS 证书验证不严格，攻击者可通过中间人攻击方式劫持支付、接口回调或其他敏感通信链路，进而影响业务正确性与数据安全。


### 5.4 系统可用性与拒绝服务风险 (Availability & DoS Risks)

除传统保密性与完整性问题外，系统在资源控制、限流熔断、内存与 I/O 使用方面也存在较多可用性风险。攻击者无需完全攻破系统，即可通过构造高频或异常请求拖垮服务。

#### 5.4.1 支付链路高并发可用性问题

支付相关逻辑在高并发场景下存在明显的资源消耗风险。

主要表现为：
- 磁盘 I/O 瓶颈：支付流程中每次请求均重复从磁盘读取私钥材料，高并发下易造成文件句柄与 I/O 资源耗尽；
- 内存溢出风险（OOM）：未对微信支付回调载荷大小进行限制，存在将超大 Payload 一次性读入内存的风险；
- 资源泄漏：如文件输入流未显式关闭，可能在并发条件下引发句柄泄漏与服务退化。

攻击者可通过构造大量请求放大上述缺陷，最终造成 JVM 内存压力、线程阻塞甚至服务不可用。

#### 5.4.2 缓存穿透与资源滥用风险

部分业务接口在参数合法性与缓存保护方面设计不足，容易被恶意请求绕过缓存层直接冲击数据库。

例如：
- 套餐列表等接口缺乏对参数范围、对象存在性及非法输入的有效过滤；

攻击者可通过批量请求不存在的 ID 或构造异常查询条件形成缓存穿透，进而放大数据库压力。

#### 5.4.3 缺乏限流、超时与连接管理机制

多个接口未配置足够的流量控制与连接保护措施，放大了 DoS 风险。

包括：
- 购物车、地址簿等接口缺乏防刷、限频或速率限制；
- 外部 HTTP 请求未设置合理超时；
- 连接未复用或释放不充分，存在线程与连接池资源耗尽风险。

该类问题虽不一定导致数据泄露，但在真实环境中极易造成服务卡顿、雪崩或局部瘫痪。

### 5.5 数据安全与隐私保护缺陷(Data Security & Privacy Issues)

系统在日志输出、敏感信息处理、个人信息展示及审计追踪方面存在明显不足，既带来现实安全风险，也可能触及个人信息保护与数据安全合规要求。

#### 5.5.1 日志敏感信息泄露

系统日志中存在输出敏感业务与身份信息的情况，可能导致低权限运维人员、日志平台使用者或攻击者通过日志直接获取高价值数据。

包括：
- 用户 Token 被直接记录在日志中，可能被利用进行账户接管；
- 微信支付解密后的明文交易数据、OpenID 等敏感字段被写入普通日志；
- 套餐、订单等业务敏感数据缺乏脱敏处理便直接输出。

日志泄露问题常被低估，但在攻击链中极具利用价值，属于需要尽快治理的问题。

#### 5.5.2 个人信息保护不足

系统涉及大量个人敏感信息与重要个人信息，如收货人姓名、联系电话、详细地址等，但缺乏足够的访问限制与展示脱敏措施。

例如：
- 地址簿中的姓名、电话、精确地址可被完整读取；
- 一旦与水平越权问题叠加，可被批量遍历和导出，形成严重隐私泄露事件。

从数据合规角度看，这类问题已明显不符合最小必要、最小可见和敏感信息保护原则。

#### 5.5.3 操作审计与溯源能力不足

后台多个关键业务操作缺乏审计日志留存，发生安全事件后难以进行责任追踪与事件还原。

未充分记录的操作包括但不限于：
- 登录、登出；
- 接单、拒单、取消订单；
- 菜品分类修改、店铺开关；
- 关键报表查看与后台敏感配置变更。

审计日志缺失会显著削弱事后取证与安全运营能力，不利于应对越权操作、内部滥用及安全事件调查。

### 5.6 输入验证与安全编码规范缺失 (Input Validation & Misconfigurations)

从代码实现质量角度看，系统在基础输入校验、参数规范化、身份绑定及安全默认配置方面仍存在较多薄弱点。这些问题虽然部分看似“编码基本功”缺陷，但往往是越权、拒绝服务和业务绕过问题的根源。

#### 5.6.1 入参校验不足

多个模块对请求参数缺乏基础合法性校验，存在空值、负值、超大值及非法格式数据直接进入业务逻辑的情况。

包括：
- 用户地址信息未严格校验完整性与有效性；
- 套餐、购物车等接口缺乏基础非空、数值范围、对象存在性校验；
- 异常参数可能直接触发底层报错，进而影响系统稳定性或暴露错误信息。

#### 5.6.2 身份绑定与操作人校验不足

系统中部分业务操作未将当前登录身份与操作对象进行严格绑定，存在冒名操作或伪造身份字段的风险。

例如：
- 创建菜单等后台操作可不填写员工 ID，或可伪造他人 ID 执行操作；
- 业务记录中的创建人、修改人、归属人等关键身份字段缺乏可信来源约束。

此类问题会进一步削弱系统内部责任边界，并与越权问题形成联动风险。

#### 5.6.3 安全默认配置不足

部分问题并非单点漏洞，而是由安全默认值设计不当导致的系统性暴露，包括弱默认密码、宽松接口访问、缺乏最小权限原则等。
这说明项目在安全基线建设与安全编码规范落实方面尚不成熟。

## 6. 综合结论（Overall Conclusion）

综合来看，Sky Take Out 当前最突出的安全问题集中在以下几个方面：访问控制缺陷、支付链路安全缺陷、后台权限边界薄弱、文件上传风险、敏感信息泄露以及缺乏限流与审计机制。其中，越权访问、支付回调校验缺失、金额校验不足、弱口令与 JWT 失效机制不完整等问题，均属于应当优先处置的高危问题。

从整体成熟度看，系统目前更接近“功能可用但安全防护不足”的典型业务项目状态。若直接用于生产环境且未进行系统性加固，存在较高概率被利用造成数据泄露、业务欺诈、账户接管或服务不可用等安全事件。


**总体结论：**  
该项目当前安全风险评级建议定为 **Critical（极高风险）**。在未完成关键问题整改前，不建议直接用于对安全性要求较高的生产环境。


## 7. 核心漏洞分析

### 7.1 越权访问与身份认证漏洞(Broken Access Control & Authentication)

#### 7.1.1 水平越权（Horizontal Privilege Escalation）

---
##### 7.1.1.1 漏洞描述 (Vulnerability Description)

系统多个业务模块存在典型的水平越权问题。服务端在接收订单 ID、地址 ID、员工 ID 等对象标识后，
通常仅依据主键执行查询或更新操作，未进一步校验目标对象是否归属于当前登录用户，或当前操作者是否具备相应权限，
导致攻击者可通过篡改或枚举资源 ID 访问、修改、删除原本不属于自己的业务数据。

该问题影响订单、地址簿、员工等多个模块，可导致未授权查看他人订单及地址信息、操作他人订单、篡改或删除他人地址数据，
以及对员工账户信息进行越权查询或修改。其本质为对象级访问控制缺失，即系统完成身份认证后，
未在具体资源访问环节落实“当前用户—目标对象—允许操作”的授权校验。

--- 

##### 7.1.1.2 缺陷代码分析 (Code Analysis)

**(1) 订单模块**

订单模块的越权问题主要体现在：接口虽然要求用户登录，但后续业务处理仅依据前端传入的订单 ID 执行查询、取消、催单、复购等操作，未校验该订单是否属于当前登录用户。

因此，攻击者只要获取或枚举到其他用户的订单 ID，即可对不属于自己的订单实施未授权访问或操作。

上述代码中，控制层直接接收路径参数`id`，并将其传入`orderService.details(id)`。
服务层内部仅调用`orderMapper.getById(id)`按订单主键查询订单，再查询其明细并返回。
整个过程中，没有将当前登录用户 ID 与订单所属用户 ID 进行绑定校验，

由于订单对象通常包含收货信息、联系电话、配送地址、订单状态、下单内容等敏感数据，该缺陷可直接导致他人订单信息泄露。
问题本质在于：系统将“知道订单`ID`”错误地等同于“有权查看该订单”

**（2） 地址簿模块**

地址簿模块存在与订单模块相同的核心问题：接口虽然面向已登录用户开放，但服务端仅依据前端传入的地址 ID 执行查询、修改、删除等操作，未校验该地址记录是否归属于当前登录用户。
由于地址簿属于典型的用户私有数据，且其中包含姓名、手机号、详细住址、性别等敏感信息，一旦缺少对象归属校验，攻击者便可通过篡改或枚举 ID 的方式访问、篡改甚至删除他人地址簿数据。

这意味着，只要攻击者持有有效登录态，就可以不断替换`URL`中的地址`ID`，尝试访问其他用户的地址信息。

更严重的是，该接口未设置有效限流或访问频次控制。
在缺少归属校验的基础上，再叠加无限制的`ID`枚举，攻击者可以通过脚本批量遍历地址`ID`，逐步“扫出”整个地址簿表中的记录。
这使问题从单点越权访问上升为批量数据泄露风险，攻击成本极低、危害范围极大。

只要攻击者知道或猜中某个地址`ID`，即可删除该条地址记录。

由于地址簿是订单提交流程的重要依赖数据，一旦他人地址被删除，用户将可能无法正常下单，或者需要重新填写信息，造成显著的业务破坏。
如果攻击者批量遍历`ID`并重复调用删除接口，甚至可以清空大量用户地址数据，影响范围将从单个账号扩大到整个平台用户。
该缺陷体现的是典型的对象级删除授权缺失。

**④ 缺陷共性：所有地址操作都仅以“主键存在”为准，而非以“归属关系”为准**

从查询、修改、删除三个接口可以看出，地址簿模块存在明显一致的危险模式：
```java
// 典型缺陷模式
addressBookMapper.getById(id);
addressBookMapper.update(addressBook);
addressBookMapper.deleteById(id);
```
也就是说，系统判断是否允许执行操作的依据，仅仅是“这个`ID`对应的记录是否存在”，而不是“当前登录用户是否拥有这条记录”。
地址簿属于强私有资源，理论上任何读取、修改、删除都必须建立在“地址记录归属于当前用户”的前提下，但当前代码完全缺失这一层访问控制。


如果服务端仅按主键进行数据访问，而不在查询条件中附加`user_id`，那么任意对象`ID`都会成为越权入口。
例如更安全的处理方式应当是按“地址 `ID` + 当前用户`ID`”联合查询记录，只有查询命中后才允许返回、更新或删除；否则应直接拒绝请求。
当前代码未体现这种设计，因此造成整个地址簿数据边界失效。

**⑤ 未限流与敏感字段明文返回进一步放大风险**
地址簿模块的问题并不止于“可越权访问”。
材料中还明确指出两点：其一，查询接口未做限流；其二，姓名、电话等敏感字段未脱敏，直接以明文形式返回。
这两点与越权缺陷叠加后，会显著放大风险等级。

未限流意味着攻击者可以自动化、高频率地遍历地址`ID`；
未脱敏则意味着一旦查询成功，攻击者获取到的是可直接利用的完整个人信息，而不是部分模糊化结果。
两者结合，会使该接口从“单条越权查询”迅速演变为“批量个人信息泄露通道”。
因此，该模块的问题不仅是业务授权缺失，也已经涉及明显的个人敏感信息保护失效。

**（3）员工模块**

员工模块存在明显的对象级访问控制缺失问题。
相关接口在接收员工`ID`或员工对象后，直接执行查询、状态修改、资料更新等操作，但未校验当前操作者是否具备对目标员工账户的管理权限，也未限制普通员工只能访问或修改自己的信息。
因此，一旦攻击者具备合法登录态，便可能通过篡改请求参数，对其他员工账户实施未授权查询、启用/禁用及资料修改等操作。


**① 启用/禁用员工接口存在未授权状态篡改风险**
```java
/**
 * 启用/禁用
 * 
 * @param status
 * @param id
 * @return Result<String>
 */
@PostMapping("/status/{status}")
public Result<String> startOrStop(@PathVariable Integer status, long id) {
    log.info("员工启用/禁用：{}, {}", status, id);
    employeeService.startOrStop(status, id);
    return Result.success();
}
```
```java
/**
 * 启用/禁用
 * 
 * @param status
 * @param id
 * 
 * @return
 */
@Override
public void startOrStop(Integer status, long id) {
    Employee employee = Employee.builder()
            .status(status)
            .id(id)
            .build();
    employeeMapper.update(employee);
}
```
上述代码中，控制层接收`status`和`id`后，直接调用`employeeService.startOrStop(status, id)`；
服务层仅构造一个`Employee`对象，并将目标员工的`id`和新的`status`设置后直接执行`employeeMapper.update(employee)`。
整个过程中，没有校验当前登录用户是否拥有管理员权限，也没有判断当前操作者是否有权变更目标员工的账户状态。

这意味着，只要攻击者能够访问该接口，就可以通过修改请求中的`id`参数，任意启用或禁用其他员工账号。
例如，普通员工可尝试将其他员工账号禁用，造成他人无法登录系统；
也可能将本应停用的账号重新启用，破坏后台账户管理秩序。
该问题本质上不是“接口没加登录”，而是登录后的权限边界完全没有落到具体对象上：
系统默认调用者可以对任意员工 ID 执行状态切换。

**② 根据`ID`查询员工接口存在越权读取风险**
```java
/**
 * 根据id查询员工
 * 
 * @param id
 * @return Result<Employee>
 */
@GetMapping("/{id}")
public Result<Employee> getById(@PathVariable long id) {
    log.info("根据id查询员工：{}", id);
    Employee employee = employeeService.getById(id);
    return Result.success(employee);
}
```
```java
/**
 * 根据id查询员工
 * 
 * @param id
 * @return
 */
@Override
public Employee getById(long id) {
    return employeeMapper.getById(id);
}
```

该查询接口的问题也非常直接。
控制层从路径参数中获取员工`ID`，服务层调用`employeeMapper.getById(id)`直接返回员工对象，没有校验当前用户是否有权查看该员工信息。
如果系统未在更高层统一限制仅管理员可访问该接口，那么任何具备访问能力的登录用户都可能通过遍历员工`ID`查询其他员工资料。

员工信息通常包含用户名、账号状态、角色信息、联系方式、创建时间、更新时间等内部管理数据，部分系统中甚至还可能附带密码哈希、工号、部门等敏感字段。
若这些字段未经严格过滤直接返回，将进一步扩大信息泄露范围。也就是说，该接口的问题在于：系统把“知道员工`ID`”错误地视为“有权查看员工信息”，从而使员工对象成为可被任意读取的目标。


**③ 修改员工资料接口存在未授权篡改风险**
```java
/**
 * 修改
 * 
 * @param employeeDTO
 * @return Result<String>
 */
@PutMapping
public Result<String> update(@RequestBody EmployeeDTO employeeDTO) {
    log.info("修改员工：{}", employeeDTO);
    employeeService.update(employeeDTO);
    return Result.success();
}
```
```java
@Override
public void update(EmployeeDTO employeeDTO) {
    Employee employee = new Employee();
    // 对象属性拷贝
    BeanUtils.copyProperties(employeeDTO, employee);
    // 设置更新时间
    // employee.setUpdateTime(LocalDateTime.now());
    // 记录当家更新人 id
    // employee.setUpdateUser(BaseContext.getCurrentId());

    // 保存到数据库
    employeeMapper.update(employee);
}
```

修改逻辑中，控制层直接接收前端传入的`EmployeeDTO`，服务层通过`BeanUtils.copyProperties(employeeDTO, employee)`将属性拷贝到实体对象，
再直接调用`employeeMapper.update(employee)`保存到数据库。 这里存在两个明显问题。

第一，没有校验目标员工记录是否允许由当前操作者修改。
如果请求体中包含的是其他员工的`id`，系统依然会照常执行更新。
这样一来，攻击者即可通过构造请求篡改他人的员工资料。

此外，由于使用`BeanUtils.copyProperties`直接复制前端提交字段，如果没有对可修改字段做白名单限制，还可能带来更广泛的参数滥用问题。
例如，攻击者可能借此修改本不应开放给前端控制的内部字段，导致风险进一步扩大。

**④ 缺陷共性：员工对象访问完全依赖前端输入，缺少角色与对象双重校验**

从启用/禁用、查询、修改三个接口可以看出，员工模块存在统一的危险模式：
```java
employeeMapper.getById(id);
employeeMapper.update(employee);
```
也就是说，系统接收到员工`ID`或员工对象后，直接将其作为数据库操作目标，
而没有进行“当前用户角色是否合法”与“当前用户是否有权操作目标员工对象”这两层关键校验。

员工模块与订单、地址簿模块相比，虽然业务属性不同，但本质问题一致：
仅完成了身份识别，没有完成细粒度授权控制。对于员工类资源，通常至少应当区分如下边界：
- 普通员工仅可查看或修改自己的有限资料；
- 管理员才能查看、修改、启停其他员工账户；
- 高敏感字段应禁止普通接口直接修改；
- 所有涉及员工对象的操作都应记录操作者身份与时间。

而当前代码没有体现上述任何一种访问控制边界，因此造成员工对象可被任意读取和变更。

##### 7.1.1.3 风险点剖析 (Root Cause Analysis)

本次漏洞并非单一接口疏漏，而是系统在访问控制设计上存在**系统性缺陷**。系统虽具备基础登录能力，能够识别“当前访问者身份”，但进入具体业务处理后，未将当前登录身份与目标数据对象的归属关系、操作权限进行强绑定校验，导致大量接口在“认证之后失去授权约束”。

**核心风险点如下：**

- **直接对象引用（IDOR）处理模式普遍存在**  
  订单 ID、地址 ID、员工 ID 等外部可控参数被直接用于 `getById`、`update`、`deleteById` 等操作，未校验“该对象是否属于当前用户”或“当前操作者是否具备管理权限”。系统默认“对象存在即允许操作”，将“知晓对象 ID”错误等同于“有权操作该对象”，破坏了用户间、员工间的数据边界。

- **认证与授权职责划分缺失**  
  系统仅停留在“用户已登录”层面，未实施对象级授权判断。例如未校验订单 `userId` 是否匹配当前用户、地址是否归属当前账号、目标员工是否允许被当前角色操作。基于“当前身份 + 目标对象 + 允许动作”的三元校验机制基本缺席。

- **服务端过度信任前端参数**  
  多个接口直接接收前端提交的 ID 或对象实体，并执行数据库操作（如主键查询、更新、删除），缺乏二次确认机制。修改接口中直接使用 `BeanUtils.copyProperties` 拷贝属性，若无字段级白名单控制，还可能导致内部字段被篡改，进一步放大风险。

- **数据访问层未内建归属约束**  
  大量代码采用单纯按主键查询/更新/删除，未将 `currentUserId`、角色信息或租户边界融入查询条件。正确的安全模型应基于“资源 ID + 当前用户 ID”联合查询，或结合角色权限判断访问范围。

- **配套安全控制不足**  
  地址簿查询接口未实施限流与数据脱敏，导致敏感信息（姓名、电话、地址）明文返回，易被批量遍历；员工模块未体现 RBAC 角色控制，普通员工即可操作他人员工资料；审计字段（如更新人、更新时间）被注释，削弱事后追踪能力。

**根本设计共性问题**在于系统缺乏“最小权限原则”和“默认拒绝原则”。无论前台用户资源还是后台管理对象，均未建立统一的“归属关系校验 + 角色权限控制”机制，导致同类问题在订单、地址簿、员工等多个模块重复出现。

综上，本次问题的根因可归纳为：
- 认证后缺少对象级授权，仅验证登录而非访问权限；
- 数据访问普遍依赖外部 ID，未绑定归属关系；
- 服务端过度信任前端参数，缺乏二次校验；
- 数据访问层未内建安全约束；
- 配套机制（如限流、脱敏、审计）缺失，进一步放大危害。

这些缺陷共同导致水平越权风险在多个业务模块同时显现，属于典型的安全架构设计问题，而非局部编码疏漏。

##### 7.1.1.4 利用方式 (Exploitation Scenario)

攻击者利用此类水平越权漏洞门槛较低，通常**无需突破登录认证或构造复杂攻击链**。仅需使用普通低权限账号登录，通过抓包修改对象 ID 参数，即可访问或操作本不属于自身的资源。利用路径简洁，具有明显的可重复性和批量化特征。

**典型利用流程：**
- 以普通用户或低权限员工身份登录；
- 定位接口中的对象 ID 参数；
- 通过枚举、递增或猜测方式篡改 ID；
- 根据响应差异确认目标并扩大范围。

**订单模块**  
攻击者可在订单详情、取消订单、再来一单、催单等接口中替换订单 ID，实现越权读取他人订单敏感信息（配送信息、联系电话等），或执行取消、复购、催单等未授权操作，干扰正常履约流程。

**地址簿模块**  
攻击者通过“根据 ID 查询地址”接口批量遍历，获取姓名、手机号、详细住址等明文敏感信息（无归属校验与限流）。进一步调用修改或删除接口，可篡改或清除他人地址记录，导致收货异常或数据破坏。

**员工模块**  
以普通员工账号登录后，篡改员工 ID 可查询、修改他人员工资料，或启用/禁用账户，扰乱后台账户体系与运营秩序。

**利用特征总结**：  
该类缺陷易自动化。在缺乏限流、风控及审计告警的情况下，攻击者可通过简单脚本对 ID 进行高速遍历，批量执行查询、修改、删除或启停操作。一旦在某一模块验证成功，相同方法可迅速迁移至其他模块，使得“知晓或猜到对象 ID”几乎等同于“控制该对象”。

##### 7.1.1.5 影响范围 (Impact)

该漏洞影响范围广泛，贯穿**用户侧核心业务数据、个人敏感信息以及后台员工管理对象**。问题同时存在于订单、地址簿、员工等多个模块，一旦被利用，将对高价值数据与关键业务流程造成系统性冲击。

**影响覆盖的模块及具体后果**如下：

- **订单模块**：越权访问订单详情、配送信息、联系电话等敏感数据，并可执行取消、再来一单、催单等操作，导致隐私泄露、履约异常及用户体验受损。
- **地址簿模块**：批量获取未脱敏的姓名、手机号、地址等隐私信息；修改或删除操作可造成地址数据污染、收货失败及配送异常。
- **员工模块**：查询、修改他人员工资料或启停账户，可能引发后台管理失控、身份混乱及运营中断。

从安全属性角度，该漏洞同时损害：
- **保密性**：未授权获取用户订单、地址及员工资料等隐私数据；
- **完整性**：篡改地址信息、员工资料及订单状态等关键数据；
- **可用性**：删除地址、取消订单、禁用员工账户等操作，影响业务连续性。

该漏洞具备显著的**批量化利用潜力**。多个接口基于可枚举 ID 设计，且缺乏限流、脱敏等控制，易导致影响从单个用户扩散至大量用户数据及多个业务模块。

从业务与合规角度，可能引发隐私泄露投诉、订单纠纷、地址数据污染、后台管理失控等后果。地址簿涉及大量个人敏感信息，若发生批量泄露，可能触发《个人信息保护法》等法规风险。

**综合来看**，该漏洞具有横向扩散快、利用成本低、危害面广的特点，属于影响范围较广、风险等级较高的系统性安全缺陷。一旦被低权限用户批量利用，可能造成大规模信息泄露、业务破坏与后台管理失控。

#### 7.1.1.6 修复建议（Remediation Recommendations）

**（1）订单模块**

**① 建立“当前用户 + 资源归属”强校验机制**

凡涉及订单、地址簿、订单明细等用户私有资源的查询、修改、取消、复用等操作，均需在服务端校验**目标资源是否属于当前登录用户**，不得仅依赖前端传入的 ID 执行逻辑。

**推荐实现方式：**

```java
Long currentUserId = BaseContext.getCurrentId();
Orders orders = orderMapper.getByIdAndUserId(id, currentUserId);

if (orders == null) {
    throw new OrderBusinessException(MessageConstant.ORDER_NOT_FOUND);
}
```
注意事项：
- 归属校验必须在业务处理前完成；
- 用户侧接口统一采用“查不到即无权”策略，避免通过错误信息差异暴露资源是否存在；
- 该校验需覆盖所有订单相关接口。

**② 数据访问层增加联合查询约束**

避免仅按主键查询的高风险写法，建议在 Mapper 层增加`id + userId`联合查询方法，将访问控制前置到 SQL 中。

示例
```java
// Mapper 接口
Orders getByIdAndUserId(@Param("id") Long id, @Param("userId") Long userId);

// SQL 示例
SELECT * FROM orders 
WHERE id = #{id} 
  AND user_id = #{userId};
```

整改范围：
- 订单详情、取消订单、催单、再来一单、地址查询、订单提交等场景；
- 订单明细查询需先校验订单归属，或通过表关联进行归属校验；
- 优先通过 DAO 层约束数据访问范围，减少 Java 代码中分散的权限判断。

**③ 逐项修复高风险接口**

- 订单详情查询接口：
在查询前使用 getByIdAndUserId 进行归属校验，若订单不存在或不属于当前用户，统一返回 ORDER_NOT_FOUND。

- 取消订单接口：
在最前置位置使用 id + userId 查询订单，完成归属校验后，再执行状态变更、退款等后续逻辑。同时增加订单状态有效性校验。

- “再来一单”接口：
必须先校验原始订单是否属于当前用户，校验通过后再复制订单明细，禁止直接根据任意 orderId 操作。

- 催单接口：
在发送消息前校验订单归属。同时建议增加频率限制、防滥用日志与告警。

- 提交订单接口中的地址归属问题：
处理`addressBookId`时必须校验地址是否属于当前用户：

```java
AddressBook addressBook = addressBookMapper.getByIdAndUserId(
    ordersSubmitDTO.getAddressBookId(), currentUserId);

if (addressBook == null) {
    throw new AddressBookBusinessException(MessageConstant.ADDRESS_BOOK_IS_NULL);
}
```

**④ 抽象统一鉴权组件**

为避免重复实现和遗漏，建议封装统一校验能力：

推荐方案：

- 封装通用方法`getUserOwnedOrderOrThrow(orderId)`；
- 或引入`authorizationService.checkOrderOwnership(orderId, userId)`等统一服务；
- 条件允许时，可采用注解 + AOP 方式进行统一拦截（适用于通用场景）。

**⑤ 统一异常返回策略**

对用户侧接口统一采用模糊化错误提示，避免资源探测攻击：
- “订单不存在或不可访问”
- “地址信息异常”
- “请求资源不存在”

真实原因仅记录在安全审计日志中。

**⑥ 补充安全审计与监控**
- 记录关键操作日志（用户ID、IP、目标资源ID、接口路径、操作结果等）；
- 对短时间内访问大量不同资源ID的行为进行告警；
- 对催单、取消等高风险操作设置风险阈值监测。

**（2）地址簿模块**

针对地址簿模块存在的水平越权、未授权篡改及未授权删除等问题，建议从**对象归属校验**、**数据访问约束**、**接口安全控制**及**审计监控**等方面开展系统性整改。地址簿属于用户私有敏感资源（包含姓名、手机号、详细住址等个人信息），其访问控制强度不应低于订单模块。本质问题是登录后仍缺少针对具体资源的归属判断。

修复需建立统一的地址簿资源访问控制机制，而非仅对单个接口打补丁。

**① 建立地址资源归属强校验机制**

凡涉及地址簿记录的查询、修改、删除、设为默认、订单引用等操作，均需在服务端校验**目标地址是否属于当前登录用户**，不得仅依赖前端传入的 ID 执行逻辑。

**推荐实现方式：**

```java
Long currentUserId = BaseContext.getCurrentId();
AddressBook addressBook = addressBookMapper.getByIdAndUserId(id, currentUserId);

if (addressBook == null) {
    throw new AddressBookBusinessException(MessageConstant.ADDRESS_BOOK_IS_NULL);
}
```
注意事项：
- 归属校验必须前置，在返回数据、执行更新或删除前完成；
- 用户侧接口统一采用“查不到即不可操作”策略，避免通过错误信息差异暴露资源是否存在；
- 需覆盖所有依赖地址 ID 的功能点，而非仅修复已发现的接口。

**② 数据访问层增加联合查询/更新/删除约束**

避免仅按主键操作的高风险模式，建议在 Mapper 层增加`id + userId`联合方法，将权限控制前置到 SQL 条件中。

示例：
```java
// Mapper 接口
AddressBook getByIdAndUserId(@Param("id") Long id, @Param("userId") Long userId);
int updateByIdAndUserId(AddressBook addressBook);
int deleteByIdAndUserId(@Param("id") Long id, @Param("userId") Long userId);
```

SQL 示例：
```sql
-- 查询
SELECT * FROM address_book
WHERE id = #{id} AND user_id = #{userId};

-- 更新
UPDATE address_book
SET consignee = #{consignee}, phone = #{phone}, ...
WHERE id = #{id} AND user_id = #{userId};

-- 删除
DELETE FROM address_book
WHERE id = #{id} AND user_id = #{userId};
```
**③ 逐项修复高风险接口**

- 根据 ID 查询地址接口：
使用`getByIdAndUserId`进行归属校验，若地址不存在或不属于当前用户，统一返回`ADDRESS_BOOK_IS_NULL`。
同时建议对返回字段进行最小化处理，手机号等敏感信息可根据场景脱敏，并增加高频查询限流与审计。

- 修改地址接口:
先校验归属，再执行更新；仅允许修改白名单字段（收货人、电话、地址、标签等），禁止覆盖`userId`、创建时间等系统字段。避免全字段透传更新。

示例逻辑：
```java
Long currentUserId = BaseContext.getCurrentId();
AddressBook dbAddress = addressBookMapper.getByIdAndUserId(addressBook.getId(), currentUserId);
if (dbAddress == null) {
throw new AddressBookBusinessException(MessageConstant.ADDRESS_BOOK_IS_NULL);
}
addressBook.setUserId(currentUserId);
// 使用 updateByIdAndUserId 执行更新
```


- 删除地址接口
删除前必须使用`deleteByIdAndUserId`校验归属；增加业务关联检查（是否为默认地址、是否唯一地址等）。
对删除操作增加频率限制与审计日志，返回模糊化错误提示。

**④ 抽象统一鉴权组件**

为避免重复实现和后续遗漏，建议封装统一校验能力：

推荐方案：
- 封装通用方法`getUserOwnedAddressOrThrow(addressId)`；
- 或引入`authorizationService.checkAddressOwnership(addressId, userId)`；
- 条件允许时，可采用注解 + AOP 进行统一拦截（适用于简单场景，不替代复杂业务校验）。

**⑤ 增强接口防护，降低批量枚举风险**
- 对查询、修改、删除接口增加单用户/单 IP 频率限制；
- 同一用户短时间内操作多个不同地址 ID 时触发告警；
- 随机化主键可作为辅助措施，但不能替代归属校验；
- 若后续支持批量操作，需对每个地址逐一校验归属。

**⑥ 统一异常返回策略**

用户侧接口统一采用模糊化错误提示，避免资源探测：

- “地址信息不存在或不可操作”
- “请求资源不存在”
- “地址信息异常”

真实原因仅记录在安全审计日志中。

**⑦ 增加审计日志与监控**

对以下关键操作记录审计日志：
- 根据 ID 查询地址
- 修改地址
- 删除地址
- 设为默认地址
- 下单时引用地址

日志字段建议包含： 用户 ID、目标地址 ID、请求 IP、接口路径、操作结果、修改前后关键字段摘要（敏感信息脱敏）。

**（3）员工模块**

针对员工模块存在的未授权状态篡改、越权读取及未授权资料修改等问题，建议从**角色权限控制**、**对象级授权校验**、**字段级访问控制**及**审计监控**等方面开展系统性整改。
与订单、地址簿等用户私有资源不同，员工模块属于后台管理类敏感资源，其访问控制核心在于校验**当前操作者是否具备相应管理权限**，而非仅关注对象归属。

修复需建立“角色权限校验 + 目标对象操作边界 + 可修改字段限制”的多层防护机制，避免“仅凭传入员工 ID 即直接执行数据库操作”的高风险模式。

**① 建立员工模块统一角色鉴权机制**

所有员工管理接口在进入核心业务前，均需校验当前操作者的角色权限。系统应至少区分以下边界：

- 普通员工：仅可查看或修改本人有限个人资料；
- 管理员：可查询、修改、启用/禁用其他员工账号（受进一步限制）；
- 高权限管理员（如存在）：操作更敏感账号，但需更严格约束。

**推荐实现方式（示例）：**

```java
Long currentUserId = BaseContext.getCurrentId();
Employee operator = employeeMapper.getById(currentUserId);

if (operator == null || !operator.isAdmin()) {
    throw new PermissionDeniedException("无权执行该操作");
}
```

注意事项：
- 不得仅凭“已登录”即默认具备管理能力；
- 建议将员工管理接口统一纳入权限框架（Spring Security / Sa-Token 等）的角色声明，避免判断逻辑分散。

**② 启用/禁用员工接口的修复建议**

该操作属于高风险账户管理行为，需实施严格授权与边界控制。

修复要点：
- 接口仅限管理员调用；
- 禁止操作者禁用自身账号；
- 禁止普通管理员禁用超级管理员或系统内置账号；

对目标员工存在性及状态合法性进行校验。

示例逻辑
```java
public void startOrStop(Integer status, Long id) {
    Long currentUserId = BaseContext.getCurrentId();
    Employee operator = employeeMapper.getById(currentUserId);
    if (operator == null || !operator.isAdmin()) {
        throw new PermissionDeniedException("无权执行员工状态管理");
    }

    if (currentUserId.equals(id)) {
        throw new EmployeeBusinessException("不允许操作当前登录账号");
    }

    Employee target = employeeMapper.getById(id);
    if (target == null) {
        throw new EmployeeBusinessException("目标员工不存在");
    }

    // 执行状态更新（建议使用带条件的更新方法）
    employeeMapper.updateStatusById(status, id);
}
```

同时建议对 status 字段增加枚举/白名单校验，仅允许合法状态值。

**③ 根据 ID 查询员工接口的修复建议**

该接口属于后台敏感信息读取场景，需实施角色限制与返回字段最小化。

修复要点：
- 仅管理员可访问管理类查询；
- 普通员工查询本人信息应使用独立接口（如`/current`），避免复用任意 ID 查询接口；
- 返回对象改为专用`VO`，仅保留业务必要字段，敏感信息（如密码哈希、内部标识）一律排除或脱敏。

**④ 修改员工资料接口的修复建议**

需区分“普通员工修改本人”与“管理员修改他人”两类场景，并实施字段白名单控制。

**普通员工修改本人**：
- 强制锁定目标为当前登录用户 ID；
- 仅允许修改昵称、联系方式、头像等有限字段，禁止修改角色、状态、用户名等关键属性。

**管理员修改他人**：
- 先校验操作者角色及目标对象可管理性；
- 仅允许更新授权范围内的字段。

禁止直接使用 BeanUtils.copyProperties 进行全字段覆盖更新，改为显式字段白名单赋值模式：
```java
Employee employee = new Employee();
employee.setId(targetId);
employee.setName(dto.getName());
employee.setPhone(dto.getPhone());
// ... 仅设置允许修改的字段
employee.setUpdateUser(currentUserId);
employeeMapper.updateByAllowedFields(employee);
```

建议为不同场景分别定义独立 DTO，避免字段混用。

**⑤ 数据访问层约束优化**

避免仅按主键直接读写的高风险模式：
- 个人资料场景：直接按当前用户 ID 查询/更新；
- 管理场景：权限校验通过后，再调用受限查询/更新方法；
- 优先通过 DAO 层条件约束降低上层遗漏风险。

**⑥ 增加关键操作审计日志**

对查询、修改、启用/禁用等操作建立完整审计记录，包含：
- 操作者 ID 及角色
- 目标员工 ID
- 接口路径、请求 IP、操作时间
- 操作类型、结果及修改前后关键字段摘要（敏感信息脱敏）

**⑦ 补充高风险操作保护措施**
- 对禁用、修改关键资料等操作增加二次确认与审计标记；
- 对超级管理员等关键账号配置特殊保护策略；
- 对查询、修改、状态切换接口增加频率限制与异常行为告警，防止批量枚举与篡改。

**⑧ 统一异常返回策略**
- 用户侧/管理侧接口统一采用模糊化错误提示，避免内部对象探测：
- “目标资源不存在或不可操作”
- “无权执行该操作”
- “请求非法”

真实原因仅记录在后台安全日志中。

#### 7.1.2 垂直越权（Horizontal Privilege Escalation）

##### 7.1.2.1 漏洞描述 (Vulnerability Description)

系统后台存在纵向越权与访问控制缺失问题。所有员工统一使用`admin`权限体系访问后台功能，系统未按角色和操作类型实施细粒度授权校验，
导致任意已登录员工均可访问员工管理、经营数据统计、运营报表等敏感功能，并可执行店铺状态切换、分类管理等高危操作。
此外，部分业务接口对资源可见状态控制不足，用户仍可访问已禁用套餐信息。
该问题可能导致敏感数据泄露、业务配置被篡改及后台功能被滥用。

##### 7.1.2.2 缺陷代码分析 (Code Analysis)

系统后台权限设计存在明显的角色边界缺失与高危操作访问控制不足问题。
当前系统仅通过是否进入`/admin/**`路径判断“后台身份”，但并未在后台内部进一步区分不同员工的角色级别、职责范围与可操作资源边界。

这意味着，只要某个员工拥有合法后台登录态，就默认具备管理员级访问能力，可以访问经营数据、执行店铺状态切换、管理员工及分类等高危操作。
此外，套餐模块在面向用户侧提供查询时，也未校验目标套餐是否处于启用状态，导致已禁用套餐仍可被普通用户访问。

上述问题表面上看是“后台统一走`admin`路径”，但本质上属于：
系统只做了后台入口身份识别，没有做后台内部细粒度授权，也没有对业务对象状态进行访问限制。

**① 后台仅区分是否登录，缺少角色分级，导致所有员工默认拥有管理员权限**
```java

registry.addInterceptor(jwtTokenAdminInterceptor)
.addPathPatterns("/admin/**")

```
```java

  */

  @RequestMapping("/admin/employee")
  @Slf4j
  @Tag(name = "EmployeeController", description = "员工管理")
```

从拦截器配置可以看到，系统仅对`/admin/**`路径统一挂载`jwtTokenAdminInterceptor`，并排除登录接口`/admin/employee/login`。
这说明后台访问控制逻辑只校验“请求是否携带合法后台员工令牌”，而没有进一步区分该员工是超级管理员、店长、运营人员，还是普通后台员工。

同时，员工管理接口直接暴露在`/admin/employee`路径下，而题述中也明确指出，`service`层没有设置任何进一步鉴权逻辑。
这意味着，只要任意员工成功登录后台，就会被系统视为具备完整后台管理能力，可以访问员工管理相关接口。

该设计本质上将“后台员工身份”和“系统管理员权限”错误地等同了起来。
由于系统中仅存在一种`admin`角色，所有员工统一纳入该角色控制，最终造成权限边界彻底消失：
- 所有员工都拥有系统最高权限；
- 所有员工都能够管理员工；
- 所有员工都能够访问后台敏感功能；
- 不同岗位之间不存在任何职责隔离。

这类问题并不属于“接口未登录保护”，而是典型的**授权模型设计缺陷**。
系统虽然拦住了未登录用户，却没有拦住“已登录但不应拥有该权限的员工”，导致后台任意员工都可执行本应仅限高权限角色的管理操作。

**② 经营数据接口未做权限隔离，导致所有员工均可访问敏感经营数据**

```java

@RequestMapping("/admin/report")
@Slf4j
public class ReportController {
  ...
}
```

经营数据接口统一暴露在`/admin/report`下，题述表明其包含用户数据统计、订单数据统计、销量排名统计、导出运营报表等功能。
这些数据显然属于高敏感经营信息，通常仅应向店长、运营负责人、财务人员或其他被明确授权的管理角色开放。

但从现有代码结构来看，ReportController同样仅依赖后台路径与后台登录态进行访问控制，未体现任何角色判断、岗位判断或数据访问范围控制。
在这样的实现方式下，所有能够登录后台的员工，都可能直接访问完整经营报表与统计数据。

这会带来较为明显的数据暴露风险。
例如，原本仅负责基础录入、订单处理或客服操作的普通员工，也可以查看门店订单走势、用户增长情况、销量排行及整体经营报表。
若系统支持导出运营报表，则敏感数据还可能被批量下载、离线传播或用于非授权分析，进一步扩大泄露影响。

该问题的根源在于：
系统默认“进入后台的员工”就等于“有权查看所有经营数据的管理员”，却没有根据岗位职责建立数据访问边界。
也就是说，经营数据这一类高敏感资源，并未被当作需要单独授权的对象，而是被错误地纳入了所有后台员工的默认可见范围。

**③ 高危后台操作未做隔离，导致普通员工可任意执行店铺状态与分类管理操作**

**a. 员工可任意切换店铺营业状态**
```java

@RestController("adminShopController")
@RequestMapping("/admin/shop")
@Slf4j
public class ShopController {

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    /**
     * 设置店铺状态 1: 营业 0: 休息
     * 
     * @param status
     * @return
     */
    @PutMapping("/{status}")
    public Result<String> setShopStatus(@PathVariable Integer status) {
        log.info("设置店铺状态: {}", status == 1 ? "营业" : "休息");
        redisTemplate.opsForValue().set("SHOP_STATUS", status);
        return Result.success();
    }

    /**
     * 获取店铺状态 1: 营业 0: 休息
     * 
     * @return
     */
    @GetMapping("/status")
    public Result<Integer> getShopStatus() {
        Integer status = (Integer) Optional.ofNullable(redisTemplate.opsForValue().get("SHOP_STATUS")).orElse(0);
        log.info("获取店铺状态: {}", status == 1 ? "营业" : "休息");
        return Result.success(status);
    }

}
```


店铺状态控制接口直接接收路径参数`status`，随后通过`redisTemplate.opsForValue().set("SHOP_STATUS", status)`直接修改全局店铺营业状态。
整个过程中，没有任何角色判断，也没有限制仅特定管理人员才能执行该操作。

这意味着，只要某个员工具备后台访问能力，就可以调用该接口任意将店铺切换为“营业”或“休息”状态。
攻击者甚至无需复杂构造，只需发送合法请求即可直接影响整个平台对外服务状态。

例如，普通员工可以将店铺强行调整为休息状态，导致前台用户无法正常下单；
也可以在不应营业的时段擅自开启营业状态，破坏门店经营安排。
由于该状态被写入全局键`SHOP_STATUS`，其影响并非局部，而是直接作用于业务运行层面。

因此，该接口并不是一个普通配置项修改点，而是典型的高危运营控制操作。
系统未将其与普通后台功能隔离，实质上等于把门店营业开关暴露给了所有后台员工。

**b.员工可任意新增、删除、修改、启停分类**

```java
/**
* 分类管理
  */
  @RestController
  @RequestMapping("/admin/category")
  @Slf4j
  public class CategoryController {
  ...
  }
```


分类管理接口同样暴露在后台统一路径下，题述表明员工可以随意执行新增分类、删除分类、更新分类、启用/禁用分类等操作。
从控制器结构看，系统并未体现任何针对分类管理能力的角色隔离机制。

分类属于直接影响前台商品展示、套餐归属与业务组织结构的重要资源。
如果任意后台员工都可以增删改查分类并切换其状态，那么将造成明显的后台管理失控。
例如，普通员工可以擅自删除线上使用中的分类，导致商品无法正常归类；
也可以启用或禁用分类，影响前台展示逻辑；
甚至可以通过构造异常分类数据扰乱菜单结构与运营秩序。

该问题与店铺状态控制问题一致，本质上并不是“接口没有登录保护”，而是：
系统把所有后台员工都当成了具备运营配置权的高权限管理员。
凡是属于业务配置、运营控制、全局状态修改类的接口，都应当与普通后台操作明确隔离，而当前实现并没有体现这种隔离。

**④ 套餐访问控制不足，导致用户可查询已禁用套餐信息**
```java
/**
* 根据套餐id查询包含的菜品列表
*
* @param id
* @return
  */
  @GetMapping("/dish/{id}")
  public Result<List<DishItemVO>> dishList(@PathVariable("id") Long id) {
  List<DishItemVO> list = setmealService.getDishItemById(id);
  return Result.success(list);
  }
  /**
* 根据id查询套餐
*
* @param id
* @return
  */
  @Override
  public SetmealVO getById(Long id) {
  List<SetmealDish> dishBySetmealId = setmealDishMapper.getDishBySetmealId(id);
  SetmealVO setmealVO = new SetmealVO();
  Setmeal setmeal = setmealMapper.getById(id);
  BeanUtils.copyProperties(setmeal, setmealVO);
  setmealVO.setSetmealDishes(dishBySetmealId);

  return setmealVO;
  }

```


套餐查询逻辑中，控制层接收套餐`id`后，直接调用`setmealService.getDishItemById(id)`或`getById(id)`获取套餐详情及其包含菜品列表。
服务层则通过`setmealMapper.getById(id)`直接查询套餐对象，并进一步组装关联菜品信息返回给前端。

问题在于，整个过程中没有看到任何关于套餐状态的校验。
也就是说，只要用户知道或猜测某个套餐`id`，系统就会直接返回该套餐信息，而不关心该套餐是否处于启用状态。

这会导致已禁用套餐仍然能够被普通用户访问。
按正常业务逻辑，禁用套餐通常意味着该套餐已下线、停售或不应再对用户展示。
但当前实现中，禁用状态并未成为访问拦截条件，导致前台用户仍可能查询到这些本不应暴露的套餐详情及其菜品组成。

这类问题本质上属于对象状态级访问控制缺失。
系统只根据id定位对象，却没有校验该对象当前是否允许被前台用户访问。
换言之，系统错误地把“套餐存在”视为“套餐可访问”，从而打破了启用/禁用状态本应承担的业务访问边界。

若被禁用套餐包含测试数据、历史菜单、错误配置或临时下线内容，该接口还可能进一步造成业务信息泄露、用户误导甚至前台业务逻辑异常。

**⑤ 缺陷共性：后台仅有单一`admin`身份，既没有角色分层，也没有高危资源与对象状态控制**

从员工管理、经营报表、店铺状态、分类管理以及套餐查询几个问题可以看出，系统存在统一且危险的授权模式缺陷：

```java
registry.addInterceptor(jwtTokenAdminInterceptor)
.addPathPatterns("/admin/**");
```


也就是说，系统只要识别调用者属于“后台员工”，就默认其可以访问整个后台资源。
而在进入具体控制器、服务层及对象操作阶段后，又没有继续做以下关键校验：
- 当前员工属于什么角色；
- 当前角色是否具备该功能权限；
- 当前角色是否能操作该类高危资源；
- 当前业务对象是否处于允许访问的状态；
- 当前员工是否仅能访问自己职责范围内的数据。

因此，系统虽然完成了“身份识别”，却没有完成真正意义上的“授权控制”。
其结果是：
- 所有后台员工共享管理员能力；
- 所有员工都可以访问经营敏感数据；
- 所有员工都可以执行高危运营操作；
- 前台用户也可以访问本应因状态限制而不可见的业务对象。

当前代码没有体现上述任何一种约束，因此造成后台权限边界整体失效，并进一步引发敏感数据暴露、高危功能滥用与对象状态绕过等一系列安全问题。

##### 7.1.2.3 风险点剖析 (Root Cause Analysis)

本次漏洞并非单个接口遗漏登录校验，而是系统在**后台授权模型、敏感功能隔离以及对象状态访问控制**方面存在系统性缺陷。系统虽能识别“请求是否来自后台员工”或“用户是否已登录”，但进入业务逻辑后，未进一步判断“员工所属角色”“角色对应权限”及“业务对象当前状态是否允许访问”，导致后台功能过度开放、前台对象状态约束失效。

**核心风险点如下：**

- **后台认证与授权职责严重混淆**  
  系统将“后台已登录员工”错误等同于“具备管理员权限的操作者”。后台接口仅通过 `/admin/**` 路径统一挂载拦截器，完成身份校验后即默认允许进入各类控制器，未根据角色（超级管理员、店长、运营、普通员工等）实施功能级授权，导致任意后台员工均可访问经营数据、员工管理、店铺状态切换、分类管理等高危功能。

- **缺乏细粒度功能授权与高危操作隔离**  
  员工管理、经营报表、店铺营业状态切换、分类增删改等接口，均未实施基于角色的权限控制。这些功能涉及敏感经营数据、账户体系和全局业务配置，本应仅限特定岗位操作，却全部默认纳入后台员工可访问范围，严重违反**最小权限原则**。

- **全局性业务控制操作缺乏保护**  
  店铺营业状态切换接口直接通过路径参数修改 Redis 全局键 `SHOP_STATUS`，影响整个平台对外服务状态；分类管理接口可影响前台菜单结构和商品展示逻辑。两者均属于全局运营控制范畴，却未设置角色校验或审批机制，普通后台员工即可直接执行。

- **敏感数据可见性控制缺失**  
  经营报表接口未遵循**最小可见原则**，任何后台员工均可查看用户统计、订单统计、销量排行等完整经营数据，缺乏岗位职责或数据范围限制，破坏企业内部数据访问边界。

- **前台对象状态访问控制缺陷**  
  套餐查询接口仅根据套餐 `id` 获取详情及菜品信息，未校验该套餐是否处于**启用状态**。系统默认“对象存在即可访问”，而非“对象处于可见/启用状态才允许访问”，导致已禁用、下线或测试状态的套餐仍可被前台用户查询，构成典型的**对象状态绕过风险**。

**根本设计共性问题**在于系统普遍存在“**路径即权限、身份即授权、对象存在即允许访问**”的错误安全假设。无论后台还是前台，均未贯彻“未明确授权则拒绝”的安全原则，缺少角色分层、细粒度授权、高危功能隔离以及对象状态校验机制。

综上，本次问题的根因可归纳为：
- 后台认证后缺少细粒度角色授权，仅验证身份而非功能权限；
- 角色模型缺失，未建立岗位职责隔离；
- 高危功能与全局控制操作未单独保护；
- 前台对象查询未纳入状态校验；
- 整体采用“默认允许”而非“默认拒绝”的访问控制策略。

这些缺陷共同导致后台资源边界与前台对象状态边界同时失效，属于典型的安全架构设计问题，而非局部实现疏漏。

##### 7.1.2.4 利用方式 (Exploitation Scenario)

攻击者利用此类缺陷**无需突破认证机制，也无需复杂攻击链**。后台越权仅需一个合法的低权限后台员工账号；前台套餐状态绕过仅需普通用户身份甚至仅知道套餐 ID，攻击门槛较低。

**后台越权利用路径：**

攻击者以普通后台员工身份登录后，由于系统未进行角色级权限校验，可直接访问原本应受限的各类接口：

- **员工管理模块**：查询、修改其他员工信息，启停员工账号，扰乱后台账户体系。
- **经营报表模块**：读取用户统计、订单统计、销量排行等敏感经营数据，并可进行导出操作，导致经营情报泄露风险。
- **店铺状态控制模块**：通过接口修改全局 `SHOP_STATUS`，恶意切换平台营业/休息状态，直接影响用户下单和门店运营。
- **分类管理模块**：增删改分类、启停分类，破坏前台菜单结构和商品展示逻辑，可能引发业务混乱。

上述操作均可通过浏览器访问、抓包重放或接口文档定位完成，且同一问题可横向扩展至其他后台模块。

**前台套餐状态绕过利用路径：**

攻击者以普通前台用户身份，通过页面浏览、抓包或 ID 猜测等方式获取套餐 ID。随后直接调用套餐详情及菜品查询接口。由于服务端未校验套餐启用状态，即便目标套餐已禁用、下线或处于测试状态，系统仍会返回完整信息。攻击者可进一步通过脚本遍历套餐 ID，批量收集已下线套餐的菜品组成、测试菜单或内部配置等敏感内容，造成业务信息泄露或用户误导。

**利用特征总结**：  
该类缺陷具有低成本、易复用、易批量化的特点。一旦发现某一高危接口未做权限控制，即可推断同类接口普遍存在相同问题，自动化利用难度低，对系统运营秩序和数据安全构成现实威胁。

##### 7.1.2.5 影响范围 (Impact)

该漏洞影响范围覆盖**后台员工权限体系、核心经营数据、高危运营控制能力以及前台套餐信息访问边界**，属于典型的**授权模型失效与对象状态控制缺失**问题。其危害具有系统性，一旦被低权限员工或普通用户利用，将对后台管理秩序、经营数据安全、门店运营状态及前台业务一致性造成多维度冲击。

**影响覆盖的模块及具体后果**如下：

- **员工管理模块**：任意已登录后台员工均可查询、修改他人员工资料，甚至执行启停操作，导致岗位职责混乱、权限扩散及内部管理失控。
- **经营报表模块**：敏感经营信息（用户统计、订单统计、销量排行、报表导出）可被无相应职责的员工访问，造成商业敏感信息泄露及非授权分析风险。
- **店铺状态控制模块**：普通员工即可切换全局营业/休息状态，直接影响用户下单和门店对外服务能力。
- **分类管理模块**：任意后台员工可增删改、启停分类，破坏前台菜单结构、商品展示及运营流程。
- **套餐查询模块**：前台普通用户可访问已禁用套餐详情及其关联菜品，导致本应隐藏的业务对象继续暴露，引发信息泄露或用户误导。

从安全属性角度，该漏洞同时损害：
- **保密性**：未授权人员可访问经营报表、员工资料及已禁用套餐数据；
- **完整性**：可任意修改员工信息、店铺状态、分类配置等关键业务数据；
- **可用性**：通过关闭营业状态、篡改分类等方式，影响正常运营和用户体验。

该漏洞具有明显的横向扩散特征：后台因统一路径拦截且仅校验登录态，导致普通员工可横向访问多个敏感模块；前台因缺乏状态校验，形成**后台权限失控 + 前台对象状态绕过**的双重影响面。

**综合来看**，该漏洞属于影响面较广、危害层级较深的系统性安全缺陷，可能引发后台管理失控、敏感经营信息泄露、核心运营配置滥用以及前台业务逻辑异常，整体风险等级较高。

##### 7.1.2.6 修复建议 (Mitigation)


针对后台接口仅校验“是否为员工登录态”、未区分角色权限、未限制高危操作范围，以及前台套餐查询未校验启用状态等问题，建议从**角色权限分层**、**高危操作隔离**、**对象状态校验**、**字段与数据范围控制**及**审计监控**等方面实施系统性整改。

问题根源在于系统将“已登录后台员工”等同于“具备完整管理员权限”，导致后台授权边界缺失；同时，对套餐等业务对象未建立基于状态的访问控制，致使禁用对象仍可被访问。

修复需建立“身份认证 + 角色授权 + 操作边界控制 + 对象状态校验”的多层防护机制，避免仅凭 `/admin/**` 路径或传入对象 ID 即直接执行敏感操作。

**① 建立后台统一角色权限控制机制**

所有后台管理接口在进入控制器或核心业务逻辑前，均需校验当前操作者的角色、岗位及对应功能权限，不得仅依据“已登录后台”默认开放全部能力。

建议至少划分以下角色边界：

- 普通后台员工：仅可访问与本人职责相关的低风险功能；
- 店长/运营人员：可访问订单处理、商品维护等授权范围内功能；
- 财务/报表人员：仅可访问经营数据与报表类资源；
- 超级管理员：可执行员工管理、系统配置、全局状态控制等高危操作。

推荐采用成熟权限框架（如 Spring Security、Sa-Token），通过角色声明、权限码或注解方式集中治理，避免权限判断分散在各 Controller/Service 中。

**② 对经营数据接口实施严格的数据访问授权**

经营数据、订单统计、销量排行、运营报表导出等接口属于高敏感资源，不应对所有后台员工默认开放。

修复要点：

- 报表类接口仅允许具备经营分析、财务或门店管理权限的角色访问；
- 导出类接口应单独配置高于普通查看的导出权限；
- 必要时增加数据范围控制（如仅允许查看所属门店或业务线数据）；
- 对批量导出操作增加审计记录与频率控制。

建议采用以下权限码进行控制：
- `REPORT_VIEW`
- `REPORT_EXPORT`
- `ORDER_STAT_VIEW`

**③ 对店铺营业状态接口进行高危操作隔离**

店铺营业/休息状态切换属于直接影响平台对外服务的高危操作，应从普通后台能力中独立隔离。

修复要点：

- 仅允许具备店铺运营控制权限的管理员调用；
- 对 `status` 参数进行枚举或白名单校验，仅允许 `0` 和 `1`；
- 增加二次确认、操作备注或审批标记；
- 记录完整审计日志（操作者、操作前后状态、请求来源、时间）；
- 对频繁切换行为增加告警与限流。

示例实现
```java
public Result<String> setShopStatus(Integer status) {
  Long currentUserId = BaseContext.getCurrentId();
  Employee operator = employeeMapper.getById(currentUserId);

  if (operator == null || !operator.hasPermission("SHOP_STATUS_UPDATE")) {
    throw new PermissionDeniedException("无权执行该操作");
  }

  if (status == null || (status != 0 && status != 1)) {
    throw new IllegalArgumentException("请求非法");
  }

  Integer oldStatus = (Integer) redisTemplate.opsForValue().get("SHOP_STATUS");
  redisTemplate.opsForValue().set("SHOP_STATUS", status);

  auditLogService.recordShopStatusChange(currentUserId, oldStatus, status);
  return Result.success();
}
```

**④ 对分类管理接口实施功能级授权与关键对象保护**

分类管理涉及商品展示结构、套餐归属及前台业务组织方式，属于业务配置类敏感资源。

修复要点：

- 分类新增、修改、删除、启停分别配置独立权限；
- 删除、禁用等高风险操作需校验是否存在关联菜品、套餐或线上数据引用；
- 对系统内置或关键分类增加保护机制，避免误删或误停用；
- 对批量操作增加限流与审计。

建议权限拆分如下：
- `CATEGORY_CREATE`
- `CATEGORY_UPDATE`
- `CATEGORY_DELETE`
- `CATEGORY_STATUS_UPDATE`

**⑤ 套餐查询接口增加对象状态级访问控制**

前台用户访问套餐详情及套餐内菜品列表时，除校验套餐是否存在外，必须同时校验其是否处于启用状态。

修复要点：

- 用户侧查询接口仅允许返回状态为“启用”的套餐；
- 禁用、下线、逻辑删除的套餐一律不得返回给普通用户；
- 若套餐不存在或不可访问，统一返回“目标资源不存在或不可访问”；
- DAO 层提供“按 ID + 启用状态”联合查询方法，避免上层遗漏校验。

对于套餐内菜品列表接口，需复用相同状态校验逻辑，防止绕过。

示例实现
```java
@Override
public SetmealVO getById(Long id) {
    Setmeal setmeal = setmealMapper.getByIdAndStatus(id, StatusConstant.ENABLE);
    if (setmeal == null) {
        throw new BusinessException("目标资源不存在或不可访问");
    }

    List<SetmealDish> dishBySetmealId = setmealDishMapper.getDishBySetmealId(id);
    SetmealVO setmealVO = new SetmealVO();
    BeanUtils.copyProperties(setmeal, setmealVO);
    setmealVO.setSetmealDishes(dishBySetmealId);
    return setmealVO;
}
```

**⑥ 数据访问层增加约束，避免仅凭主键直接读写敏感对象**

优化建议：

- 用户侧资源查询：在 DAO 层直接限定为“当前用户可访问对象”；
- 后台管理资源：在权限校验通过后，调用带限制条件的 DAO 方法；
- 对象访问优先使用“ID + 状态 + 范围”联合条件，而非裸 `getById()`；
- 更新操作优先采用条件更新，防止误更新或越权更新。

示例方法：
- 套餐：`getByIdAndStatus(id, ENABLE)`
- 分类：`updateStatusByIdWithPermissionCheck(...)`

**⑦ 增加字段级访问控制与白名单更新机制**

后台涉及配置类、人员类、经营类资源的修改接口，禁止直接对前端传入对象进行整对象覆盖更新。

修复要点：

- 不得使用 `BeanUtils.copyProperties()` 将前端 DTO 全量覆盖到数据库实体；
- 仅允许显式更新授权字段；
- 对状态、角色、排序值、门店归属等关键字段单独控制，低权限角色不得修改；
- 不同场景使用独立 DTO，避免高权限字段与普通业务字段混用。

推荐采用白名单赋值方式进行更新：
```java
Category category = new Category();
category.setId(dto.getId());
category.setName(dto.getName());
category.setSort(dto.getSort());
category.setUpdateUser(currentUserId);
categoryMapper.updateByAllowedFields(category);
```

**⑧ 建立关键后台操作审计与安全监控机制**

对经营数据访问、店铺状态切换、分类增删改、套餐状态调整等行为建立完整审计机制。

审计内容应包含：
- 操作者 ID、账号、角色；
- 目标对象 ID、对象类型；
- 接口路径、请求方法、来源 IP；
- 请求时间、操作类型、执行结果；
- 修改前后关键字段摘要（敏感信息脱敏）。

同时增加以下监控能力：
- 频繁访问经营数据接口的告警；
- 高频切换店铺状态、批量删除分类等异常操作的告警；
- 禁用对象被频繁访问的安全监控；
- 后台敏感接口的访问频率限制与异常行为识别。

**⑨ 统一异常返回策略，防止接口探测与对象枚举**

敏感接口应避免向前端暴露精确的内部错误信息，防止资源探测或权限探测。

建议统一返回模糊化提示，例如：
- “目标资源不存在或不可访问”
- “无权执行该操作”
- “请求非法”

真实错误原因及详细异常信息仅记录于后台日志和审计系统。

**⑩ 从架构层面重构“后台统一 admin 即全权限”的错误模型**

本次问题根源在于将“后台员工身份”与“系统管理员能力”混为一体，导致所有后台员工天然共享高权限。

整改应从授权模型整体修复，建立完整的分层授权体系：

- 身份认证：确认是否为合法后台员工；
- 角色授权：确认所属角色；
- 功能权限：确认是否可访问当前接口；
- 数据范围：确认可操作的数据范围；
- 对象状态：确认目标对象是否允许访问或修改；
- 高危保护：对全局状态、经营数据、配置类资源增加额外约束。

只有构建上述分层授权体系，才能从根本上消除“任意后台员工均可访问敏感数据、执行高危操作、绕过对象状态限制”的系统性安全缺陷。

#### 7.1.3 认证与会话管理缺陷

##### 7.1.3.1 漏洞描述 (Vulnerability Description)
系统在认证与会话管理方面存在明显缺陷。
后台员工密码仅采用弱 MD5 方式存储，默认口令设置过于简单，且未强制首次登录后修改，导致账号口令安全性较低。
同时，登录接口缺少验证码、失败次数限制、账户锁定、IP 限制等暴力破解防护措施，攻击者可对后台账号持续进行口令猜测。
另一方面，系统登出后未对 JWT 进行服务端失效控制，缺乏黑名单、吊销或版本校验机制，导致令牌在有效期内仍可继续使用。
整体来看，系统在密码保护、登录防护与会话失效机制等关键环节均存在不足，可能引发账号被破解、会话被滥用及未授权访问等安全风险。

---

##### 7.1.3.2 缺陷代码分析 (Code Analysis)

**① 密码仅使用弱 MD5 存储，缺乏现代密码散列保护机制**

```java
employee.setPassword(DigestUtils.md5DigestAsHex(PasswordConstant.DEFAULT_PASSWORD.getBytes()));
```

从员工密码初始化逻辑可见，系统在保存密码时，仅对明文口令进行一次 **MD5** 计算后直接写入数据库。

这种处理方式虽避免了明文存储，但未能满足现代密码安全存储的基本要求。

**MD5** 并非专为密码保护设计的散列函数，其主要缺陷包括：
- 计算速度极快，抗暴力破解能力弱；
- 未使用随机盐值（salt）机制；
- 相同密码会产生完全相同的散列值。

一旦数据库泄露，攻击者可利用彩虹表、字典攻击或高速枚举，快速批量还原大量用户口令。

**核心问题**：密码存储机制设计不当。  
系统未采用 **bcrypt、scrypt、PBKDF2 或 Argon2** 等具备加盐和高计算成本的现代密码散列算法，
导致员工口令在数据库泄露场景下无法得到有效保护。


**② 默认密码设置过弱，且未强制员工首次登录后修改密码**

```java
public class PasswordConstant {

    public static final String DEFAULT_PASSWORD = "123456";

}
```

从代码中可见，系统将后台员工的**初始密码**统一设置为 `123456`。

该密码属于典型弱口令，极易遭受暴力破解、撞库攻击或人工猜测。

更严重的是，当前实现中完全缺失“首次登录必须修改密码”的强制逻辑。
新建员工账号后，若员工未主动修改，账户将长期维持默认弱口令状态。
攻击者仅需知道用户名，即可通过极少尝试直接登录后台。

此类问题在后台管理系统中风险尤为突出：
- 默认密码全系统统一，具备**批量利用**特征；
- 员工安全意识不足时，弱口令可能长期存在，形成持久攻击面。

**核心缺陷**：默认凭据设计不当 + 口令生命周期管理缺失。  
系统既未设置足够强的初始密码，也未通过流程机制强制用户在首次登录时更新密码，导致整个后台认证体系从源头即处于薄弱状态。


**③ 登录接口缺乏爆破防护，易遭受暴力破解与口令枚举攻击**

```java
/**
 * 登录
 *
 * @param employeeLoginDTO
 * @return
 */
@Operation(summary = "登录")
@Parameters({
        @Parameter(name = "employeeLoginDTO", description = "登录信息", required = true)
})
@PostMapping("/login")
public Result<EmployeeLoginVO> login(@RequestBody EmployeeLoginDTO employeeLoginDTO) {
    log.info("员工登录：{}", employeeLoginDTO);

    Employee employee = employeeService.login(employeeLoginDTO);

    // 登录成功后，生成jwt令牌
    Map<String, Object> claims = new HashMap<>();
    claims.put(JwtClaimsConstant.EMP_ID, employee.getId());
    String token = JwtUtil.createJWT(
            jwtProperties.getAdminSecretKey(),
            jwtProperties.getAdminTtl(),
            claims);

    EmployeeLoginVO employeeLoginVO = EmployeeLoginVO.builder()
            .id(employee.getId())
            .userName(employee.getUsername())
            .name(employee.getName())
            .token(token)
            .build();

    return Result.success(employeeLoginVO);
}
```

```java
/**
 * 员工登录
 *
 * @param employeeLoginDTO
 * @return
 */
public Employee login(EmployeeLoginDTO employeeLoginDTO) {
    String username = employeeLoginDTO.getUsername();
    String password = employeeLoginDTO.getPassword();

    // 1、根据用户名查询数据库中的数据
    Employee employee = employeeMapper.getByUsername(username);

    // 2、处理各种异常情况（用户名不存在、密码不对、账号被锁定）
    if (employee == null) {
        // 账号不存在
        throw new AccountNotFoundException(MessageConstant.ACCOUNT_NOT_FOUND);
    }

    // 密码比对
    // 进行md5加密，然后再进行比对
    password = DigestUtils.md5DigestAsHex(password.getBytes());
    if (!password.equals(employee.getPassword())) {
        // 密码错误
        throw new PasswordErrorException(MessageConstant.PASSWORD_ERROR);
    }

    if (employee.getStatus() == StatusConstant.DISABLE) {
        // 账号被锁定
        throw new AccountLockedException(MessageConstant.ACCOUNT_LOCKED);
    }

    // 3、返回实体对象
    return employee;
}
```

从登录接口与服务层认证逻辑可见，系统的认证流程仅包含“根据用户名查询用户”“校验密码匹配”“检查账户状态”三个基本步骤。

整个过程**完全缺失**以下关键防御机制：
- 验证码或人机校验
- 登录失败次数限制与临时锁定
- IP/时间窗频率控制
- 异常登录监测

攻击者可对登录接口持续高频发起口令尝试，系统不会进行任何阻断。即使同一账户密码错误数百次，认证逻辑仍会正常执行查询与比对。

结合前述**默认弱密码**（`123456`）和**MD5明文散列**问题，登录接口极易成为暴力破解突破口。

此外，异常处理逻辑暴露了账号存在性：
- 用户名不存在时抛出 `AccountNotFoundException`
- 密码错误时抛出 `PasswordErrorException`

若前端响应区分不同错误，攻击者可先进行用户名枚举，再针对真实账户持续爆破，大幅提升攻击效率。

代码中虽存在账号锁定判断：

```java
if (employee.getStatus() == StatusConstant.DISABLE) {
    throw new AccountLockedException(MessageConstant.ACCOUNT_LOCKED);
}
````

但该状态并非由登录失败自动触发，而是人工维护或业务预置，并非真正的失败锁定机制。

**核心缺陷**：认证接口缺乏抗暴力破解能力。
系统仅将登录视为简单校验过程，未对高频攻击入口进行任何安全加固，导致弱口令和默认口令极易被自动化撞出，后台高权限账户面临较高风险。



**④ 登出操作仅返回成功结果，JWT 未真正失效，会话失效机制不完整**

```java
/**
 * 退出
 *
 * @return
 */
@PostMapping("/logout")
public Result<String> logout() {
    return Result.success();
}
```

从退出接口实现可以看到，系统在收到登出请求后仅直接返回成功结果，并没有执行任何与令牌失效相关的服务端处理逻辑。
而当前系统使用 JWT 作为后台认证凭据，登录成功后由服务端签发令牌交由客户端持有：

```java
String token = JwtUtil.createJWT(
        jwtProperties.getAdminSecretKey(),
        jwtProperties.getAdminTtl(),
        claims);
```

JWT 具有**自包含、无状态**的特点。令牌一旦签发，只要未过期且签名合法，服务端就会认可其身份。

当前登出接口仅在前端层面生效，**完全缺失服务端主动失效机制**。  
若 JWT 在登出前已被泄露、窃取或保留在缓存、代理、抓包记录中，攻击者仍可继续使用该令牌访问后台接口，直至自然过期。

代码中未实现以下任何常见 JWT 失效控制方式：
- Redis 黑名单机制
- Token 版本号 / 会话版本控制
- 服务端会话状态绑定
- 登出后刷新用户密钥或失效时间戳
- 高风险场景下的主动吊销机制

**核心缺陷**：会话失效控制链条缺失。  
系统完成了 JWT 签发，却无法主动撤销已签发的有效令牌，导致“退出登录”在服务端层面缺乏实际安全意义，后台接口持续面临已泄露 Token 的利用风险。


**⑤ 缺陷共性：系统实现了基础身份校验，却缺少完整的口令安全、认证防护与会话控制体系**

系统虽实现了基础身份校验，但**缺失完整的口令安全、认证防护与会话控制体系**。

核心问题体现在以下环节：

- 口令层面：使用弱 **MD5** 单次散列存储密码，并统一设置默认口令 `123456`
- 登录接口：完全缺乏验证码、失败次数限制、IP 频率控制等抗暴力破解机制
- 会话层面：JWT 登出仅前端生效，**无服务端主动失效机制**（黑名单、版本控制等）

代码片段示例：
```java
employee.setPassword(DigestUtils.md5DigestAsHex(PasswordConstant.DEFAULT_PASSWORD.getBytes()));
public static final String DEFAULT_PASSWORD = "123456";
@PostMapping("/login")
@PostMapping("/logout")
````

**结果**：系统仅完成“能登录、能拿 Token、能访问后台”的功能闭环，却未建立安全防护闭环。

具体风险包括：

* 数据库泄露后密码易被快速破解
* 新建账号因默认弱口令极易被猜中
* 登录接口易遭自动化爆破
* 登出后已泄露 Token 仍可继续使用

**核心缺陷**：认证安全设计不完整，导致后台身份认证机制整体偏弱，易形成多点突破风险。

##### 7.1.3.3 风险点剖析 (Root Cause Analysis)

本次漏洞风险并非源于单一接口缺陷，而是系统在**身份认证安全设计**上存在系统性薄弱环节。虽然已实现“用户名 + 密码 + JWT”的基础登录闭环，但口令保护、认证入口防护及会话失效控制等关键环节安全措施明显不足，导致后台账号体系多点暴露可利用攻击面。

**主要风险点**如下：

- **密码存储机制薄弱**：员工密码仅进行一次 MD5 计算后存入数据库，未使用随机盐值，也未采用现代密码散列算法（如 bcrypt、Argon2）。MD5 运算速度快且无自适应成本，一旦数据库泄露，攻击者可通过彩虹表、字典攻击或高速枚举快速还原大量密码，实际保护能力严重不足。

- **默认凭据设计不安全**：后台员工默认密码统一设置为 `123456`，属于典型弱口令。系统未实现首次登录强制修改密码、密码复杂度校验、历史口令限制及定期轮换等口令生命周期管理机制，导致新建账号长期处于可预测、可批量利用的状态。

- **认证入口防护缺失**：登录接口仅完成用户名查询、MD5 密码比对及账号状态检查，未实现验证码、人机校验、登录失败次数限制、临时锁定、IP 频率限制等任何抗爆破措施。同时，用户名不存在与密码错误返回不同异常，可能为攻击者提供用户名枚举便利，使定向爆破效率显著提升。

- **账号状态检查机制不足**：系统仅对 `DISABLE` 状态进行静态检查，未建立基于失败次数的动态锁定或同一来源异常尝试的风控机制，未能有效阻断自动化攻击。

- **JWT 会话管理缺陷**：退出登录接口仅返回成功结果，未在服务端执行 Token 吊销、黑名单标记、会话版本更新或 Redis 状态失效等操作。JWT 一旦签发，在有效期内即持续有效，导致“退出登录”无法真正终止会话，泄露或窃取的 Token 可被持续复用。

上述缺陷相互关联，形成**复合风险链条**：弱 MD5 存储降低离线破解门槛，默认弱口令增加在线猜解概率，缺失爆破防护使攻击者可低成本反复尝试，而会话失效机制缺失则导致已获取凭据难以被及时阻断。整体根因在于系统更侧重认证功能可用性，而未落实**纵深防御**和**凭据全生命周期保护**原则。

---

##### 7.1.3.4 利用方式 (Exploitation Scenario)

攻击者利用此类缺陷门槛较低，无需复杂漏洞链，仅需针对暴露的后台登录接口，即可围绕默认弱口令、无爆破防护及 JWT 无法主动失效等弱点展开攻击。

**典型攻击路径**包括：

- **在线爆破与用户名枚举**：收集或猜测后台员工用户名后，使用脚本向登录接口高频尝试默认密码（如 `123456`）或常见弱口令组合。因系统无验证码、频率限制及失败锁定机制，攻击者可长时间持续尝试。差异化的错误响应进一步支持先枚举真实用户名，再进行定向爆破。

- **数据库泄露后的离线破解**：获取密码表后，利用未加盐的单次 MD5 散列，通过彩虹表、字典库或 GPU 工具快速批量还原密码，尤其对默认弱口令效果显著。

- **JWT 会话接管**：成功登录后获取 JWT 令牌。若 Token 通过抓包、缓存、日志或浏览器存储等方式泄露，攻击者即可在有效期内持续使用该令牌访问后台接口。即使受害者执行退出登录，因服务端未进行 Token 吊销，会话仍可被复用。

攻击过程高度适合**脚本化、批量化和自动化**执行，可实现低成本账号接管、后台未授权访问及会话持久滥用。

**典型利用流程**：
1. 收集或猜测后台员工用户名；
2. 调用登录接口，利用默认弱口令或常见组合进行持续尝试；
3. 根据响应差异枚举真实账号并缩小爆破范围；
4. 成功登录后获取 JWT 令牌；
5. 使用令牌访问后台管理接口；
6. 即使后续退出登录，只要 Token 未过期，仍可继续复用；
7. 若获得数据库散列值，可进一步开展离线破解扩大影响。

---

##### 7.1.3.5 影响范围 (Impact)

该漏洞影响覆盖**后台员工认证体系、密码存储、登录防护及会话控制机制**，属于身份认证安全设计薄弱与会话管理缺陷的叠加问题。其危害贯穿账号创建、密码存储、登录认证至退出登录的完整链路，可能导致后台账户批量接管、认证边界失守及敏感权限被冒用。

**受影响模块及具体后果**：

- **员工账号初始化模块**：统一默认密码 `123456` 且未强制首次改密，新建账号长期处于弱认证状态，易被低成本登录攻击。
- **密码存储模块**：单次 MD5 无盐存储，数据库泄露后密码可被快速破解，扩大后台失陷范围。
- **后台登录认证模块**：缺乏抗爆破防护，结合弱口令与 MD5 缺陷，易遭受撞库、猜解及批量尝试。
- **账号枚举阶段**：差异化错误响应便于用户名枚举，提升定向爆破成功率。
- **后台会话控制模块**：退出登录未执行服务端 Token 吊销，泄露 Token 可在有效期内持续复用。

从安全属性角度，该漏洞同时损害：
- **保密性**：密码可被破解，后台敏感数据与管理功能面临泄露风险。
- **完整性**：账户接管后，攻击者可对系统配置及业务数据进行未授权修改、删除等操作。
- **可用性**：持续爆破或会话滥用可干扰正常管理秩序，甚至导致后台功能被恶意操控。

**综合来看**，该问题呈现明显的**链式利用特征**，形成“弱口令入口 + 低强度存储 + 无爆破防护 + 会话无法主动失效”的连续攻击链。一旦被利用，可能引发后台员工账户批量失陷、敏感权限滥用及泄露会话长期可复用等严重后果，整体风险等级较高。

##### 7.1.3.6 修复建议 (Mitigation)

针对员工认证模块中**弱密码存储、默认口令过弱、登录接口缺乏爆破防护、JWT 登出未真正失效**等问题，建议从密码存储机制、初始凭据管理、认证接口防护、会话失效控制及安全审计监测等方面开展系统性整改。核心目标是建立“**强口令散列 + 首次登录改密 + 登录防爆破 + Token 可撤销 + 审计监控**”的完整安全防护链路，避免仅实现“校验成功即发放 Token”的薄弱认证模式。

**主要修复建议**如下：

**① 密码存储机制升级**：  
  停止使用 MD5 等快速散列算法，改用 **bcrypt、PBKDF2、scrypt 或 Argon2** 等专用于密码保护的自适应算法。  
  - 使用算法内置盐值，确保相同密码生成不同散列；  
  - 配置合理计算成本，提高离线破解门槛；  
  - 登录校验统一调用密码编码器的 `matches` 方法。  

  **推荐实现（Spring Security BCrypt 示例）**：

  ```java
  PasswordEncoder passwordEncoder = new BCryptPasswordEncoder();

  // 创建员工时
  employee.setPassword(passwordEncoder.encode(initPassword));

  // 登录校验时
  if (!passwordEncoder.matches(employeeLoginDTO.getPassword(), employee.getPassword())) {
      throw new PasswordErrorException("用户名或密码错误");
  }
````

**迁移方案**：新密码按新算法存储，老用户首次登录成功后自动升级散列格式，或通过强制重置完成全量迁移。

**② 初始化密码策略整改**：
  取消统一弱默认密码（如 `123456`），改为生成**随机高强度临时密码**或通过安全激活链接初始化。

  * 为账户增加 `mustChangePassword` 等标识位；
  * 首次登录仅允许访问改密接口，修改完成前禁止进入后台；
  * 强制密码满足长度、大小写、数字、特殊字符等复杂度要求。

  **推荐逻辑示例**：

  ```java
  String tempPassword = RandomPasswordUtil.generate(16);
  employee.setPassword(passwordEncoder.encode(tempPassword));
  employee.setMustChangePassword(true);
  employeeMapper.insert(employee);
  ```

  登录成功后检查：

  ```java
  if (Boolean.TRUE.equals(employee.getMustChangePassword())) {
      throw new PasswordResetRequiredException("首次登录请先修改密码");
  }
  ```

  临时密码通过安全渠道一次性下发，并设置较短有效期。

**③ 登录接口增加抗暴力破解机制**：
  对登录失败次数、IP 频率、异常行为实施有效控制。

  * 单账号连续失败 5 次临时锁定 15 分钟；
  * 高风险场景启用验证码或人机校验；
  * 使用 Redis 实现失败计数与时间窗控制；
  * “用户名不存在”与“密码错误”统一返回相同提示，防止用户名枚举。

  **示例逻辑**：

  ```java
  String lockKey = "login:fail:" + username;
  Integer failCount = redisTemplate.opsForValue().get(lockKey);
  if (failCount != null && failCount >= 5) {
      throw new AccountLockedException("账号已临时锁定，请稍后再试");
  }

  if (employee == null || !passwordEncoder.matches(...)) {
      redisTemplate.opsForValue().increment(lockKey);
      redisTemplate.expire(lockKey, Duration.ofMinutes(15));
      throw new LoginFailedException("用户名或密码错误");
  }

  redisTemplate.delete(lockKey);
  ```

  同步建议：接口限流、WAF 拦截、多维度限速（账号/IP/设备指纹）。

**④ 账号状态与失败锁定机制分离**：
  将人工禁用与登录失败锁定设计为独立字段（如 `status` 与 `lockUntil`、`loginFailCount`）。
  登录流程中分别判断禁用状态与锁定期，避免逻辑耦合与审计混淆。

  **示例**：

  ```java
  if (employee.getStatus() == StatusConstant.DISABLE) {
      throw new AccountLockedException("账号已被禁用");
  }
  if (employee.getLockUntil() != null && employee.getLockUntil().isAfter(LocalDateTime.now())) {
      throw new AccountLockedException("账号已临时锁定，请稍后再试");
  }
  ```

  登录成功后重置失败次数与锁定状态。

**⑤ JWT 会话控制整改**：
  建立服务端 Token 撤销机制，避免“伪登出”。
  推荐方案：Redis 黑名单（基于 `jti` 或完整 Token）、Token 版本号、最后登出时间戳等。

  **黑名单方案示例**：

  ```java
  @PostMapping("/logout")
  public Result<String> logout(HttpServletRequest request) {
      String token = request.getHeader("token");
      Claims claims = JwtUtil.parseJWT(...);
      long ttl = claims.getExpiration().getTime() - System.currentTimeMillis();
      if (ttl > 0) {
          redisTemplate.opsForValue().set("jwt:blacklist:" + token, "1", ttl, TimeUnit.MILLISECONDS);
      }
      return Result.success();
  }
  ```

  认证过滤器中增加黑名单校验。同时缩短 JWT 有效期，支持 Access + Refresh Token 模式，并在密码修改、禁用、权限变更时立即吊销旧 Token。

**⑥ 补充审计日志与异常响应统一**：
  对登录成功/失败、密码修改、登出、Token 吊销等行为记录完整审计日志（用户名、IP、User-Agent、结果、失败原因等），高风险事件触发告警。
  登录失败统一返回“用户名或密码错误”，真实原因仅写入日志，防止信息侧漏。

**⑦ 数据库与配置层同步加固**：

  * 密码字段预留足够长度以兼容强散列值；
  * 配置中心不得明文保存默认密码；
  * 后台登录接口强制使用 HTTPS；
  * JWT 密钥安全托管并定期轮换；
  * 敏感安全参数实现可配置化；
  * 日志中禁止打印明文密码、完整 Token 或散列值。

通过上述整改，可有效提升认证体系的纵深防御能力，显著降低账号被接管、爆破及会话滥用的风险。
